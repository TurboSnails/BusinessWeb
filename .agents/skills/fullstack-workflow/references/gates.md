# 质量门禁与审批门

质量门禁由机器判定，审批门由用户判定。两者都不接受 Agent 的口头保证。

## 质量门禁（按模式）

| 门禁 | 快速 | 标准 | 严格 | 判定 |
| --- | --- | --- | --- | --- |
| lint + 格式 | ✓ | ✓ | ✓ | 零错误 |
| 类型检查 | ✓ | ✓ | ✓ | 零错误 |
| 单元测试 | ✓ | ✓ | ✓ | 全绿；新增代码有对应测试 |
| 构建 | ✓ | ✓ | ✓ | 所有目标（web、api、mobile）构建成功 |
| 集成测试（API、DB） | 涉及时 | ✓ | ✓ | 全绿；用真实数据库副本或容器 |
| E2E / 浏览器验收 | — | 涉及 UI 时 | ✓ | 关键路径脚本通过，附截图或录屏 |
| 契约检查 | — | 涉及 API 时 | ✓ | OpenAPI / schema 与实现一致；破坏性变更需版本号 |
| 安全扫描 | — | 建议 | ✓ | 依赖漏洞无高危；仓库无密钥泄漏 |
| 迁移演练 | — | 涉及 DB 时 | ✓ | 在副本上 up → down → up 成功，记录耗时 |
| 性能基线 | — | 涉及性能需求时 | ✓ | 与 design.md 中的指标对比，不劣化 |
| `/opsx:verify` | — | ✓ | ✓ | 实现与 specs 无未解释差异 |
| 覆盖率 | — | 不低于基线 | 不低于基线 | 以 CI 报告为准 |

规则：
- CI 是唯一判定来源。本地结果只用于预检；验证报告里必须写 CI 运行链接或 job 标识。
- 跳过的测试要在验证报告里逐条列出原因；没有原因的跳过视为失败。
- 门禁失败回到 ⑤，由原 Implementer 修，Reviewer 复审，不允许“先合了再说”。

## 审批门（必须用户授权）

遇到下列任一操作，Orchestrator 停下，给出 影响面、不可逆程度、回滚方案、建议执行窗口，等待用户逐项明确授权。授权只对本次操作有效，不延伸到下一次。

| 操作 | 必须先给出 |
| --- | --- |
| 破坏性数据库迁移（删列/表、改类型、大表重写） | 受影响行数、备份方式、down 迁移是否验证过 |
| 生产部署 | staging 验收结果、灰度策略、回滚命令 |
| 密钥、证书、权限、IAM 变更 | 变更前后对比、泄漏风险、轮换计划 |
| 删除或导出用户数据 | 法律依据、范围、是否可恢复 |
| 支付、计费、结算逻辑 | 金额测试用例、对账方式 |
| 改 CI/CD 流水线本身 | 为什么不能在应用层解决 |
| 第三方服务开通或付费 | 费用、数据流向 |

用户未回复时不执行，也不拆成小步绕过。

## 落地清单：流程之外还要配什么

三个工具加起来不是自动化平台。要做到“一句话下需求，Agent 持续执行，失败自动修，最后交付”，项目里还需要：

- [ ] **Orchestrator 状态持久化**：任务卡与回执落盘（例如 `openspec/changes/<change>/runs/`），会话中断能恢复；用 `dev-team` 时它的检查点机制可复用。
- [ ] **执行沙箱**：Implementer 在容器或受限 worktree 里跑测试；禁止直接连生产库与真实密钥。
- [ ] **CI/CD**：PR 触发上表门禁；主分支保护，必须 CI 绿 + 一个非作者审查。
- [ ] **审批门实现**：生产部署与迁移走受保护环境或手动批准步骤，Agent 没有直接执行权限。
- [ ] **可观测性**：部署后有错误率、延迟、关键业务指标看板，供 ⑦ 的观察窗使用。
- [ ] **回滚演练**：至少演练过一次回滚，记录在 release-checklist。

缺项不阻塞开发，但要在 proposal.md 的“风险”里写明当前缺哪一项、靠什么人工手段补。
